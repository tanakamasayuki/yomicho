# 読み帳（yomicho）仕様

## 0. この文書について

策定中の仕様書。決まったことと未決のことを分けて書く。

実装の都合より、**辞書の扱いを単純に保つこと**を優先する。記号や記法は仮置きで、あとで変えてよい。

## 1. 何を作るか

日本語の原稿にルビを振る、あるいは読み上げ用のテキストを作るためのツール。

### 自動変換ではなく翻訳メモリ

類似ツールの多くは**自動変換型**で、原稿を入れると解析器が読みを推定して出力する。辞書は補正のおまけで、人の判断は蓄積されず、解析器を更新すると同じ原稿の結果が変わる。

読み帳は**翻訳メモリ型**とする。蓄積された辞書が主であり、解析器は初回の下書きを作る補助にすぎない。

> 一度決めた読みは、参照辞書が後から変わっても変わらない。

これが最上位の要件。以下の設計はすべてこの再現性を守るためにある。

### 動く場所

CLI を最優先とする。同じコアをブラウザと VSCode 拡張から使えるようにしておく。

## 2. 全体の流れ

```
  update    原稿を走査して原稿辞書に見出しを追加する（参照辞書を引く）
     ↓
  人の編集  記号を消す、読みを埋める
     ↓
  build     原稿辞書だけで変換する（参照辞書を読まない）
```

推定や提案といった「賢い処理」は update に閉じ込める。build は決定論的で、解析器も参照辞書も要らない。

この分離のおかげで、ブラウザ版は辞書ファイルだけで動く。形態素解析器の辞書をブラウザに持ち込む必要がない。

## 3. 辞書ファイル

### 3.1 形式

タブ区切りのテキスト。1行1エントリ。

```text
日本橋	にほんばし
技術書	ぎじゅつしょ
未確定語	
```

| 列 | 内容 | 省略 |
|---|---|---|
| 1 | 見出し | 必須 |
| 2 | 読み（先頭1文字が状態記号） | 必須（空欄可） |
| 3 | スニペット（作業用） | 省略可 |

3列目は変換に一切影響しない。`cut -f1,2` で辞書そのものが取り出せる。

### 3.2 状態記号

読み欄の先頭1文字で状態を表す。

| 表記 | 状態 | 人がすること |
|---|---|---|
| `にほんばし` | 確定・ルビを振る | なし |
| `#カレント` | 確定・ルビを振らない（読みは持つ） | なし |
| `#` | 確定・ルビを振らない・読みも不要 | なし |
| `!やま` / `!` | フィルターの対象外（→ 8.1）。ルビを振らない | なし |
| `?` | 収集しただけ。語かどうか怪しい（→ 7.2） | なし。拾いたければ `?` を消す |
| `>にほんばし` | 参照辞書から引いた（未レビュー） | 任意 |
| `+にほんばし` | 機械や AI が入れた（未承認） | 確認して `+` を消す |
| （空欄） | 未定 | 読みを書く |

すべての編集が1文字の操作になる。承認は `+` を消すだけ、非表示化は `+` を `#` に打ち替えるだけ。

`#` に読みを書けるのは、ルビは振らないが読み上げでは読ませたい場合のため。読みも要らない誤検出は `#` だけを書く。

`!` は update が機械的に付ける。読みは空でよく、そのために読みを探しに行く必要はない。判定を覆したい場合は `!` を消せば、以後は人の判断として扱われる（→ 4.3）。逆にフィルターが拾わなかった語を除外したい場合は `#` を書く。

`?` は `--full` で拾った「語かどうか怪しいもの」を記録するための状態。**他の記号と違い、照合に参加しない。** 非語が中の実在する語を巻き添えにしてしまうためで、`センサユニット	?` があっても `センサ` にはルビが付く。スニペットも付けない。`?` を消せば空欄になり、次の update でスニペットが付いて作業ゾーンに入る。

記号は**当面は既定固定**とする。設定で変更可能にすると、辞書ファイル単体で読めなくなり、別環境で静かに誤動作する。→ [9. 設定](#9-設定)

### 3.3 見出しの文脈指定

見出しの一部を `{ }` で囲むと、**囲んだ部分だけが置換の対象**になり、囲みの外側は照合にのみ使われる。

```text
日本橋	にほんばし
大阪の{日本橋}	にっぽんばし
{今日}中	きょう
今日{中}	じゅう
```

読み欄は常に**対象の読み**を表す。囲みを使わない場合は見出し全体が対象。

後ろ2行は対になっている。`今日中` に対して `今日` を きょう、`中` を じゅう と振る。文脈は消費されない（→ 5.2）ので、互いの文脈になりながら両方が成立する。

これがないと、読み欄の意味が「見出しの読み」から「弁別のための札」にすり替わる。たとえば `大阪の日本橋	にっぽんばし` と書くと、ルビ出力では「大阪の」にまでルビが乗り、読み上げ出力では「おおさかの」が消える。

対象は1つの連続した範囲でなければならない。以下はエラー。

```text
大阪の{日本橋	     閉じていない
{大阪の日本橋}	     対象が全体（囲む意味がない）
大阪の{}日本橋	     対象が空
```

**囲み記号は仮置き。**

### 3.4 読みの割り当て

読み欄に `/` を入れると、漢字1文字ずつに読みを割り当てる（モノルビ）。`/` がなければ見出し全体に1つ（グループルビ）。

```text
日本橋	に/ほん/ばし     日(に)本(ほん)橋(ばし)
取り扱い	と/あつか        取(と)り扱(あつか)い ─ 仮名の位置は見出しから決まる
本気	マジ             本気(マジ) ─ 当て字
一日	ついたち         一日(ついたち) ─ 熟字訓
```

`/` の数は見出しに含まれる漢字の数と一致していなければならない。一致しない場合はエラー。

**`/` を取り除けば全体の読みになる**ので、読み上げ出力とも両立する。

総ルビや学年別ルビは漢字1文字ごとに振るか振らないかを決めるため、この割り当てが前提になる。書かれていない場合は自動で割り当てを試み、曖昧なときはグループルビに倒したうえで「要確認」として報告する。

### 3.5 スニペット

3列目には、その語が原稿のどこに出たかを示す短い抜粋を書く。

```text
日本橋駅	+にほんばしえき	大阪の{日本橋駅}では乗り換えが
未知製品		新型の{未知製品}を発表した
```

- **要対応の行（`+` と空欄）にだけ付く。** 承認して記号が消えれば、次の update で自動的に外れる
- **今回の原稿に出現した行にだけ付く。** 書き換えていない章の未解決行にはスニペットが無いので、目で区別できる（→ 6.3）
- 対象を `{ }` で囲む。3.3 と同じ記法
- 連続する空白は1つにまとめる。本文抽出後のプレーンテキストから取る

用途は2つ。

**AI に埋めてもらう。** 未解決の行をそのまま貼れば、文脈込みで読みを推定できる。表記だけ渡しても `未知製品` は読めない。戻ってきたものは必ず `+` を付けて取り込み、無条件に確定させない。

**自分で確認する。** 空欄を見て「これ何の話だったか」と原稿を検索しに行く往復が消える。AI を使わなくても効く。

スニペットはそのまま**文脈付き見出しの下書き**になる。両端を削って1列目に移せば 3.3 のエントリになる。

```text
日本橋	+にほんばし	大阪の{日本橋}では乗り換えが
   ↓ 「大阪のときだけ にっぽんばし」と気づいたら、3列目を1列目に移して削る
大阪の{日本橋}	にっぽんばし
```

### 3.6 並び順

update のたびに次の順で並べ替える。

```
1. 記号なし（確定）
2. #
3. !
4. ?
5. >
6. +          ← 作業ゾーン
7. （空欄）    ← 作業ゾーン
```

同じ状態の中は見出し順。

**ファイルの下端がそのまま作業リストになる。**片付いた行は次の実行で上に移動するので、下端が縮んでいくのが進捗表示を兼ねる。

## 4. 辞書の階層

### 4.1 参照辞書は複数指定できる

指定した順に見て、**見つからなければ次を見る**。最初に見つかった辞書の値を採用する。

```sh
yomicho update book.md -d series.tsv -d global.tsv
```

この場合の探索順は、

```
book.tsv（原稿辞書）→ series.tsv → global.tsv
```

原稿辞書が常に最優先で、参照辞書は指定順。どこにも無ければ未知語として扱う。

### 4.2 空欄も値

見出しが存在すれば、読みが空欄でもそこで探索を打ち切る。下位の辞書にフォールバックしない。

```text
global.tsv:  日本橋	にほんばし
book.tsv:    日本橋	
```

この原稿では `日本橋` は未解決になる。`にほんばし` は採用されない。

参照辞書の最新値を採り直したければ、原稿辞書の**該当行を削除**する。

### 4.3 update は既存の行を書き換えない

update がすることは2つだけ。

- 原稿に出現した見出しのうち、原稿辞書に**無いもの**を追加する
- 要対応の行のスニペットを更新する

既存の行の読みには一切触らない。空欄の行も、`>` の行も、そのまま残す。

これにより、update をいつ何度実行しても人の判断は失われない。既存行が変わるのは、人がその行を消したときと `--force` を付けたときだけ。

## 5. マッチ

### 5.1 手順

```
1. 探索順に従って有効な辞書を1つに解決する
2. 原稿の全位置で、見出し全体（文脈を含む）を照合し、候補を列挙する
3. 各候補は自分の「対象範囲」だけを主張する
4. 対象範囲が重なる候補どうしで勝者を決める
     a) 全体の一致長が長い方（＝文脈が多い方）
     b) 同じなら対象が長い方
     c) それも同じなら探索順で先の辞書
5. 誰にも主張されなかった範囲は通常処理
```

### 5.2 文脈は消費されない

文脈部分は照合に使われるだけで、置換の対象にはならない。したがって**他のエントリの対象になれる**。

```
原稿:   大阪の日本橋
辞書:   大阪	おおさか
        大阪の{日本橋}	にっぽんばし

結果:   大阪(おおさか)の 日本橋(にっぽんばし)
```

総ルビではこの性質が必須になる。

### 5.3 英数字トークンは分割しない

英字を1文字以上含む `[A-Za-z0-9_+.-]` の連続を**ひとかたまり**として扱い、その途中で区切ってルビを付けない。トークン全体をちょうど1エントリで覆えたときだけルビを出し、覆えなければ無ルビにして未解決として報告する。

日本語側の最長一致とは独立した規則である。

```text
辞書: BMP ビーエムピー / cm センチ

BMP280   → 無ルビ・未解決     BMP だけ拾うと 280 が読まれず誤り
20cm     → 無ルビ・未解決     cm だけ拾うと 20 が読まれず誤り
BMP用     → BMP(ビーエムピー)用(よう)    トークンの外の日本語は普通に拾う
```

部品の読みをつないで全体の読みを組み立てる処理（`ESP32` + `KeyBridge`）は行わない。これは提案の仕事であり、build は「1エントリで覆えるか」だけを見る。→ 12

### 5.4 保護区間

次を対象外とする。

| 種類 | 例 |
|---|---|
| フロントマター | 先頭の `---` から `---` まで（Marp のスライド区切りは対象外） |
| コードフェンス | ` ``` ` / `~~~` の囲み |
| インラインコード | `` `...` `` |
| HTML コメント | `<!-- ... -->` |
| `<style>` `<script>` | **中身ごと**。CSS のセレクタが本文として拾われるため |
| HTML タグ | `<img src="...">` などタグ本体 |
| 既存のルビ | `<ruby>...</ruby>` |
| URL | `https://...` |
| 画像のラベル | `![h:450]` — Marp では表示されない指示子 |
| リンク先 | `](...)` |

**リンクのラベル `[日本橋](...)` は保護しない。** 表示される本文だから。画像のラベルとは扱いが逆になる。

保護区間は**位置の範囲（start, end）のリスト**として持ち、その外側だけを処理する。文字列を置換して退避する方式は取らない。プレースホルダが原稿の内容と衝突する事故を構造的に避けるためと、VSCode 拡張が同じ位置情報をそのまま使えるため。

括弧の中身を一律に除外することはしない。

### 5.5 変換が満たす性質

build は次を必ず満たす。正解データを用意しなくても検査できるので、テストとして維持する。

- `strip(build(x))` が元の原稿と一致する（往復して原稿が壊れない）
- `build` が冪等である
- 保護区間の中身が1文字も変わらない
- ルビの親文字が仮名だけになることがない
- ルビが入れ子にならない

加えて、**誤った読みを出すくらいなら出さない**。語の一部だけにルビを付けることはせず、読みが決まらないものは無ルビにして未解決として報告する。

## 6. 原稿辞書

### 6.1 ロックファイルとして扱う

原稿辞書には、その原稿で**使ったエントリがすべて**入る。参照辞書から引いたものも含めて全部。

したがって原稿辞書1つで変換が再現する。

- 参照辞書が無い環境、他人の環境、CI でも同じ出力になる
- 参照辞書が変わっても、壊れても、過去の原稿は無傷
- build は参照辞書を読まない（読む必要がない）

`package.json` と `package-lock.json` の関係にあたる。育てるのは参照辞書、記録するのが原稿辞書。

### 6.2 3つの層

| 状態 | 性質 | 扱い |
|---|---|---|
| 記号なし / `#` | 人の判断 | 絶対に消さない |
| `+` / 空欄 | 作業中 | 消さない（作業が巻き戻る） |
| `>` / `!` / `?` | 機械のキャッシュ | 捨てて再生成できる |

`>` と `!` と `?` だけが機械的に再生成できる。`>` は参照辞書から、`!` はフィルターから、どちらも決定論的に求め直せる。`+` は解析器や AI が出したもので引き直せないため、捨てない。

### 6.3 未使用語

原稿から消えた語は、既定では削除しない。人の判断が資産だから。章を書き直して語が消え、また戻したときに読みが生きている方が実用的。

代わりに、**未解決の報告は今回の原稿に出現した語だけに絞る**。スニペットが付いていない空欄行は今回出現していないので、埋めなくてよいことが目で分かる。

## 7. コマンド

```
build       原稿辞書だけで変換する。参照辞書を読まない
update      原稿を走査して原稿辞書に見出しを追加する。参照辞書を引く
unresolved  要対応の行を TSV で書き出す
merge       外から戻ってきた読みを取り込む
```

### 7.1 build

原稿辞書だけを読み、5章の規則で変換する。参照辞書も解析器も既知文字リストも読まない。

満たすべき性質は 5.5 のとおり。

### 7.2 update

次の順に行う。既存の行は書き換えない（→ 4.3）。

```
1. 原稿辞書と参照辞書を重ねて照合する
     一致した見出しが原稿辞書に無ければ、参照辞書から引いて `>` を付けて足す
2. 覆えなかった範囲から候補を切り出す
     参照辞書にあれば `>`、既知文字だけなら `!`、どちらでもなければ空欄で足す
3. スニペットを整える
     要対応かつ今回の原稿に出た行に付け、それ以外の行からは外す
4. 3.6 の順に並べ替えて書き出す
```

**候補の切り出しには `Intl.Segmenter`（`granularity: 'word'`）を使う。** JavaScript の標準機能なので追加の依存も辞書も要らず、Node でもブラウザでも同じ結果になる。

英数字トークンは 5.3 のとおり丸ごと1候補にする。

切り出し方は差し替えられるようにしておく。ただし既定を変えると原稿辞書に入る見出しが変わるので、比較して選ぶこと。

**数字を含む英数字トークンは `?` にする。** 型番・量・生の値であって、普通ルビを振らないものだからである。

**ドットを含むものも同じ。** ファイル名・メソッド名・ドメインばかりで、読ませたいものがない。ハイフンは逆で、`E-Paper` `ESP-IDF` `Lang-ship` のように名前に使われるので対象にしない。

```text
KeyBridge  Arduino  E-Paper  ESP-IDF        → 空欄（作業ゾーン）。名前なので読みを決める
BMP280  SHT40  U001-D  CUR-01  Checker3     → `?`。型番
10cm  20cm  100cm  562us  940nm             → `?`。量。`cm` 1つの判断を回数分聞いても意味がない
0xFFE01F  1920x1080  5x7                    → `?`。そもそもルビを振りたくない
sketch.yaml  Serial.begin  .h  lang-ship.com → `?`。ファイル名・メソッド名・ドメイン
```

型番でも読ませたいものはある（`M5Stack` `ESP32` `CH32V003`）。ただしそれらは参照辞書に登録済みで作業ゾーンには来ない。ここで判断するのは**未登録のものだけ**なので、「新しく出てきた英数字混じりは型番」と賭けるほうが当たる。

どちらにしても**出力は変わらない**。5.3 の規則により、トークンの一部にはどのみちルビが付かないので、`?`（照合しない）と空欄（照合してブロック）で結果が同じになる。作業ゾーンに置くかどうかだけの違いである。

**副作用**: `ESP32KeyBridge` `PCMFlowG711` のような、部品が登録済みの複合名も `?` に回る。これらは合成で `+` 提案できる対象なので、合成を入れたときに作業ゾーンへ戻ってくる。→ 12

**`--full`** を付けると、さらに通常は捨てている候補も `?` として記録する。カタカナ語（2文字以上）と、英字を含まない数値のかたまりが対象。ひらがなはそのまま読めるので拾わない。

いずれも基本は放置してよく、読みが要ると分かったときだけ `?` を消して拾い上げる。作業ゾーンは増えない。

**既知の限界: 複合語は分かれる。** `未知製品` は `未知` と `製品` の2候補になり、ひとまとまりでは提案されない。読みは誤らない（それぞれ正しく読める）が、長い固有名詞は人が登録することになる。漢字の連続をひとかたまりにする方式も試したが、`一度` `一番` `両面` のような短い漢語が非語に結合されてしまい、精度は落ちた。

### 7.3 unresolved と merge

3.5 の往復を担う2つ。

```sh
yomicho unresolved book.md            # 要対応の行を TSV で出す
yomicho merge book.md < filled.tsv    # 読みを取り込む
```

`unresolved` は**今回の原稿に出現した要対応の行だけ**を、原稿辞書と同じ TSV の形で出す。整形しないので、そのまま貼ってそのまま戻せる。

`merge` は寛容に受ける。列数は2でも3でもよく、記号は付いていてもいなくてもよい。そのうえで次を守る。

- 取り込んだ読みには**必ず `+` を付ける**。外から来たものを無条件に確定させない
- **人の判断が入っている行は上書きしない。** 確定・`#`・`>` の行は見送り、件数を報告する
- 原稿辞書に無い見出しは取り込まず、件数を報告する

ツール自体に AI を組み込まない。貼りやすい形式にするだけで、モデルにもサービスにも縛られない。

### 7.4 引き直しは「消してから update」

参照辞書の値を採り直す仕組みは1つだけ。

> **行を消せば、次の update で参照辞書から引き直される。**

語単位なら、エディタでその行を削除して update するだけでよい。専用のコマンドもオプションも要らない。

これは `>` の行に限らない。記号なしの行を消せば、自分の判断を捨てて参照辞書の値に戻せる（→ 4.2）。「消す」が唯一の引き直しの合図になる。

### 7.5 強制更新

`>` `!` `?` の行をまとめて捨てるショートカットを用意する。

```sh
yomicho update book.md --force
```

`>` `!` `?` の行をすべて削除してから通常の update を実行するのと同じ。参照辞書やフィルターを差し替えたときに使う。頻度は低い想定。

- 記号なし・`#`・`+`・空欄の行には触れない。**人の判断と作業中の行は `--force` でも失われない**
- 参照辞書から消えた見出しは、update の通常動作どおり空欄になる。元の値は残らない
- `>` `!` `?` の行を手で書き換えていた場合、その変更は失われる。残したいなら記号を消して自分の判断にしておく
- 実行後に、追加・削除・値の変化した件数を報告する

引き直し専用のロジックは持たない。削除と update の組み合わせで説明できる範囲に留める。

## 8. フィルターと出力

### 8.1 フィルター

**既知文字のリスト**を与えると、そこに含まれる文字だけで構成される語にはルビを振らない。

判定は update が行い、対象外になった語には `!` を付ける。build はフィルターを知らず、`!` の行を飛ばすだけでよい。

これにより「モード」という独立した設定が要らなくなる。

| やりたいこと | 与える既知文字リスト |
|---|---|
| 総ルビ | 渡さない（すべてが対象） |
| 学年別 | その学年までに習う漢字 |
| 難読語のみ | 自分が「読めて当然」とみなす漢字 |

いずれも同じ仕組みで、リストの中身が違うだけ。学年という設定項目は存在せず、渡すリストの内容がそれにあたる。

リストは文字を並べただけのテキストとする。学年別漢字配当表はその形で公開されているので、そのまま持ち込める。

**未定**: リストの具体的な形式、指定方法、プリセットを同梱するかどうか。→ 12

### 8.2 `!` を書き出さないオプション

対象外の語を `!` として残さず、そもそも辞書に書かない選択もできる。

| | 既定（`!` を残す） | 書き出さない |
|---|---|---|
| 辞書の大きさ | 原稿に出た語がすべて載る | フィルターを通った語だけ |
| ルビが振られない理由 | 辞書を見れば分かる | 分からない |
| 参照辞書から引いた読み | `!` の行に残る | 失われる |
| その語が原稿に出たか | 辞書を見れば分かる | 分からない |

**既定は残す側**とする。「使った辞書のデータが全部ローカルにある」という原稿辞書の性格（→ 6.1）に沿うため。辞書が大きくなりすぎる場合や、理由を辞書に残す必要がない場合に書き出さない側を選ぶ。

どちらでも変換結果は変わらない。`!` の行は出力に影響しないため。

### 8.3 出力の種類

| 種類 | 内容 |
|---|---|
| ルビ | 原稿にルビを付与したものを出す |
| 読み上げ | 本文を読みに置換したテキストを出す |
| 校正 | 原稿を変換せず、未解決や不整合を報告する |

8.1 のフィルターと直交する。総ルビ・学年別・難読語のみは出力の種類ではなく、フィルターの違いである。

読み上げについて一点。`!` の語は読みを持たないことがあるため、**全文をかなに変換することはできない**。読み上げ出力は「TTS が間違える語にだけ読みを与える」形になる。全文かな化が必要な場合は、フィルターを外して取り込み直す。

### 8.4 記法

ルビの出力記法は複数を想定する（HTML `<ruby>`、青空文庫、Re:VIEW、Markdown 拡張）。

**未定**: 具体。→ 12

## 9. 設定

**当面は設定ファイルを作らない。** CLI 引数だけで足りる。

辞書ファイルに設定を書くことはしない。辞書は update のたびに機械が全行を書き直すファイルであり、そこに人の記述を混ぜると書き戻しのたびにコメントや順序の保存が必要になる。

> 機械が書くファイルと、人が書くファイルを分ける。

これを守れば辞書のパーサは「タブで割って2列」だけで済み、`grep` `sort` `cut` がそのまま効く。

設定ファイルが必要になったときも、ini や toml のような形式を発明せず、**CLI 引数の既定値を並べるだけ**のファイルにする。

```
--mode=grade
--grade=3
--dict=../global.tsv
```

パーサは行を引数配列に足すだけで済み、覚えることが CLI 引数の1セットに収まる。

## 10. 実装方針

### 10.1 構成

**単一の npm パッケージ**とし、プラットフォーム差分は `src/` の中で分ける。モノレポにはしない。

```
bin/yomicho.js       CLI エントリ
src/index.js         コア。I/O なし・依存ゼロ
src/node/            Node アダプタ（ファイル入出力、保護区間の検出、レポート）
src/browser/         ブラウザアダプタ
web/                 プレイグラウンドのソース
scripts/build-site.js  web/ + src/ → site/
docs/                ドキュメント
test/
```

`package.json` の `exports` で入口を出し分ける。

| 入口 | 中身 | 依存 |
|---|---|---|
| `.` | コア。辞書の解析・階層解決・マッチ・割り当て・出力整形 | なし |
| `./node` | Node アダプタ | Node 組み込みのみ |
| `./browser` | ブラウザアダプタ | なし |

コアは **I/O を持たない純粋関数の集合**とする。入力は文字列、出力は文字列か構造体。Node の組み込みモジュールを import しない。依存パッケージを持たない。

これだけ守れば、Node でも Deno でも Bun でもブラウザでも VSCode の拡張ホストでも無改造で動く。

**バンドルは作らない。** コアが依存ゼロの ESM なので、npm も GitHub Pages も `src/` をそのまま配れる。CDN 向けの最小化ファイルが必要になったら足す。

**VSCode 拡張は別リポジトリ**とする。拡張は独自の packaging を持つため、同居させると `files` と `exports` が濁る。npm に公開したパッケージへ依存させればよい。

### 10.2 解析器の位置

形態素解析器は core の外に置き、update の提案生成にだけ使う。差し替え可能なプラグイン境界とする。

build に解析器が要らないため、ブラウザ版に十数 MB の辞書を持ち込む必要がない。

フィルターも同様に update 側だけに置く。build は `!` の行を飛ばすだけで、既知文字リストを読む必要がない。

### 10.3 進め方

CLI を先に作る。コアの仕様が固まってからブラウザ版を足し、VSCode 拡張はさらに後に別リポジトリで作る。

解析器の選定は後回しにできる。CLI の第1版は辞書だけで動かし、辞書解決・割り当て・出力の仕様を先に確定させる。

### 10.4 リポジトリの約束

決めた理由が残りにくいものを書いておく。

**ドキュメントは日本語のみ。** `README.md` の先頭に英語の要約を数行だけ置き、その下から日本語本体を続ける。`README.ja.md` は作らない。ルビ・熟字訓・送り仮名・学年別配当表といった概念は英語で書くと長くなるうえ、例が全部日本語なので対訳を維持する意味が薄い。入口だけ英語にして、探し回らせないために「ドキュメントは日本語のみ」と明記する。

`docs/` の中は `.ja.md` を使う。`.md` = 英語、`.ja.md` = 日本語という規則なので、`.ja.md` しか無いこと自体が日本語のみを意味する。索引（`docs/README.md`）は作らず、ルートの `README.md` から個別のドキュメントへ直接リンクする。

**プレイグラウンドは GitHub Actions で公開する。** Pages のソースに選べるのは `/` か `/docs` か Actions だが、`docs/` はドキュメントで埋まっているので Actions 一択になる。`web/` は公開ディレクトリではなくソースで、`scripts/build-site.js` が `web/` と `src/` を `site/` へ集めて `.nojekyll` を置き、ワークフローがそれをアーティファクトとして上げる。`site/` はコミットしない。

**Web UI も日本語のみ。** 多言語化の仕組み（locale の JSON とその同期チェック）を持たない。

## 11. 判断の基準

機能の取捨には次の一本を使う。

> **その機能は、人が触る行数を減らすか。**

翻訳メモリでいうレバレッジ率にあたる。減らさない機能は最小仕様に入れない。

GUI が必要に見える場面は「候補から選ばせる」ときだが、それは常に「候補を全部テキスト行として書き出して、人に間違いを消させる」に置き換えられる。この置き換えが効く限り、GUI なしで進める。

## 12. 未決事項

### 記法
- 状態記号の文字（`>` `+` `#` `!`）— 仮置き
- 文脈の囲み記号 — `{ }` か `【 】` か
- 割り当ての区切り — `/` で確定してよいか
- コメント行を導入するか（`#` は `C#` や `#` 自体が見出しになり得るので使えない）

### 辞書
- 文字の正規化 — NFC を掛けるか、全角半角や旧字体を同一視するか。既定は「正規化しない・完全一致」を想定
- 同一辞書内に同じ見出しが複数ある場合の扱い
- 読みの表記 — ひらがな限定か、カタカナや記号も許すか
- 参照辞書を「手で育てる核」と「過去の原稿辞書の集積」に分けるか

### フィルター
- **出力時フィルター** — build 側で取り込み時とは別のフィルターを掛けられるようにするか。同じ原稿から小3版と小5版を1つの辞書で出せるようになる。`/` があれば漢字単位、無ければ語単位で判定でき、`/` は前提ではなく精度の問題。ただし読みが空の `!` 行は振れないため、フィルターを広げる方向には限界がある
- 既知文字リストの形式 — 1行1文字か、他の並べ方か
- リストに読みを持たせるか — 1文字の読みは複合語では当てにならない（`橋` は `日本橋` では ばし）ので、持たせるなら読み上げ用の参考値という位置づけになる
- プリセット（学年別配当表など）を同梱するか、利用者が用意するか
- 語の一部だけが既知文字の場合の扱い — 現状は「全部が既知なら対象外」なので、学年3で `高機能` は語全体にルビが付く。漢字ごとに振り分けるには `/` による割り当てが要る
- ルビが振られない理由を build 側で説明する仕組み（`!` を書き出さない設定のとき、辞書から理由が読めなくなるため）

### 英数字・単位
- **単位付き数値の組み合わせ爆発** — 5.3 の規則により `0.5A` `1A` `1.2A` `3A` `12V` `18W` `20cm` `940nm` をそれぞれ登録することになる。数値が増えるたびに行が増える
- 読みの中で**数字は数字のまま**書く表記（`12V` → `12ボルト`）を前提にすると、必要なのは「数字はそれ自身として読む」という規則だけで、`A` → `アンペア` の1行で `0.5A` も `3A` も覆える
- ただし `A` を単独のエントリにすると、本文中の `A` にまで `アンペア` が付く。**「部品としてのみ使う」エントリ**という区別が要る。別辞書にするか、状態記号を増やすか
- 部品の連結（`ESP32` + `KeyBridge`、`20` + `cm`）は辞書が決まれば一意に定まるが、**決定論であっても正しいとは限らない**。区切り記号を落とすと `0-5mm` → `05ミリ`、`DC5.5-2.1` → `ディーシー5.52.1` のように壊れる。したがって build の規則にはせず、**update が `+` で提案する**のが正しい置き場所になる
- 英単語・型番の日本語読みを与える汎用辞書は存在しない。`M5Stack` の `5` を「ファイブ」、`ESP32` の `32` を「サンニー」とするような好みは一律の数字変換では表せない

### 推定
- 読み推定エンジンをそもそも入れるか。入れるなら選定 — 現状 update は読みを推定せず、参照辞書に無い語は空欄で足すだけ
- 既知エントリからの合成提案をどこまでやるか（`日本橋駅` = `日本橋` + `駅`）
- 複合語がひとまとまりで提案されない件（→ 7.2）への対処。長い候補を併記して人に選ばせるか、そのままにするか

### 出力
- ルビの出力記法の具体
- 初出のみルビを振るモード、およびその範囲（文書 / 章 / スライド）

### インターフェース
- コマンドラインの指定方法全般 — 本文中の `-d` や `--force` は説明のための仮の表記であり、確定した構文ではない
- サブコマンドの区切り方（build / update を分けるか、1コマンドのオプションにするか）

### 機能
- 昇格 — 原稿辞書で決めた読みを参照辞書に戻すコマンド
- 逆抽出 — すでにルビが振られた原稿から辞書を作る
- 不整合の検出 — 同じ見出しが原稿ごとに違う読みになっている箇所の報告
- スニペットの長さと切り出し単位（固定文字数か文単位か）
- **表の中のスニペットが役に立たない** — 前後がセル区切りになり、読みの手がかりにならない。表の行では見出し行を添えるなど別の取り方が要る
- 同形異音語で、文脈に手がかりが無い場合の扱い（当面は未解決として報告するに留める）
